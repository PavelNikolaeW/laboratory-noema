# Реализация и приёмка

## 1. Порядок реализации

### Шаг 1. Контракт и чистый движок

Прочитать PUBLIC_API.md и PRIVATE_ENGINE.md. Описать Pydantic DTO с запретом лишних полей, Decimal/enum-валидаторами, разделить public/private модели. Реализовать переходы и development fixtures S1–S4. Сгенерировать публичную OpenAPI без приватных схем. Зафиксировать выбранные зависимости и версии.

Результат: расчёты работают без HTTP/UI/LLM; эталонные рецепты подтверждают достижимость заказов. Реализация не должна содержать case-specific проверки вида «если партия S1, вернуть 73».

### Шаг 2. Хранение и durable операции

Run/batch/sample/operation/observation/event/order/recipe/submission/note/prediction. Транзакции принятия и завершения, idempotency keys, блокировка входов, outbox, восстановление running после restart. Приватные данные не сериализуются общим `model_dump` в публичный ответ.

Результат: CLI или интеграционный тест полностью выполняет эксперимент и восстанавливается после принудительного restart.

### Шаг 3. Публичный API и тонкий клиент

Реализовать PUBLIC_API.md, pagination, статус и события. Создать только транспортный async Python-клиент с публичными типами и примером poll/resume. Клиент не содержит готовых экспериментальных стратегий или моделей мира.

Проверить схему с разработчиком харнеса: base URL, token, операции, ошибки, polling cursor и соответствие operation IDs. Изменения breaking-контракта сопровождаются новой версией, а не расходящимися копиями документации.

### Шаг 4. UI человека

Рабочий стол: заказ, партии, образцы, действия, журналы, блокнот, сравнение и редактор рецепта. Реальные запросы в тот же API. Значения «не измерено», «измерено до обработки» и «результат неизвестен клиенту» различимы. Полная работа с клавиатуры; ошибки и ожидание видимы; корректный layout от 360 px.

Результат: человек выполняет S1 без терминала, пишет гипотезу и проверяет рецепт на свежей порции. UI сохраняет заметки и resume после обновления страницы.

### Шаг 5. Оценка и управляемое изменение

Заказы S1–S4, independent validation, метрики, paired run creation, закрытая CLI изменения gain между операциями. Публичный и закрытый экспорт журналов раздельные. Режим notified/undisclosed явный и сохранён в протоколе.

Результат: baseline-рецепт перестаёт работать после изменения, исправленный работает, а истинная причина не выдаётся через публичный ответ.

### Шаг 6. Интеграция и пилот

Запустить лабораторию независимо; передать харнесу публичный контракт/клиент и изолированные credentials. Проверить accepted → waiting → event → result. Провести человеческий пилот, затем агентный smoke. Шум, износ и Heroes III пока не реализовывать.

## 2. Приёмочные проверки

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| L01 | split/separate/mix на наборе состояний | Суммарная масса сохраняется с заданным допуском; нет отрицательных компонентов |
| L02 | heat/cool и активация | Охлаждение не обращает активацию, heat не меняет массу |
| L03 | Смешаны активированная и исходная порции | Частичная активация сохраняется корректно; горячая смесь применяет порог |
| L04 | S1/S2/S3 эталонные рецепты | Числа и успех соответствуют PRIVATE_ENGINE.md |
| L05 | S4 до/после смены gain | Старый рецепт fail после изменения, исправленный pass |
| L06 | Повторные измерения без обработки | В базовом режиме одинаковы, revision не увеличен |
| L07 | Публичный GET после heat | Старое наблюдение остаётся на прежнем revision; не обновлено без измерения |
| L08 | Повтор принятого POST с тем же ключом | Тот же ID/результат, одно списание и один эффект |
| L09 | Тот же ключ с другим телом или маршрутом | 409, без эффекта |
| L10 | Два одновременных запроса на одну порцию/прибор | Один принят; другой busy/stale; нет двойного потребления |
| L11 | Consumed sample либо один ID дважды в mix | Отказ до эффекта |
| L12 | Бюджет/материал недостаточны | Нет принятой операции и отрицательного остатка |
| L13 | Crash до commit эффекта | Возможен повтор вычисления; итоговый эффект один |
| L14 | Crash после commit до HTTP/event доставки | Результат восстанавливается, материал не расходуется повторно |
| L15 | Polling и pagination с повтором cursor | События не теряются, ID стабильны, порядок sequence сохраняется |
| L16 | REST/DTO/OpenAPI/error/UI bundles | Нет скрытых полей, формул, seed, конфигов, ответов evaluation |
| L17 | Чужие run IDs/admin endpoint | Доступ закрыт, нельзя сбросить run/бюджет токеном участника |
| L18 | Номинальный и измеренный состав UI | Номинальная масса не выдаётся за новое измерение; состав вообще не передан |
| L19 | Prediction создан после принятия target operation | Нельзя связать задним числом; запись неизменяема |
| L20 | Submission на свежих порциях | Рецепт реально воспроизведён; success не доверяет наблюдениям участника |
| L21 | Подмена продукта стандартом/другой партией | Проверка использует только свежую целевую партию |
| L22 | Принята проверка, затем изменяется прибор | Один submission использует один snapshot; интервенция ждёт безопасную границу |
| L23 | Cost comparison | Разделены исследование, итоговый рецепт, verification и расходы LLM |
| L24 | UI после refresh | Заметки, операции, журнал и выбранное прохождение восстанавливаются |
| L25 | Одинаковые действия через UI/клиент | Одинаковые видимые результаты и расход при одинаковой конфигурации |
| L26 | Долгая пауза/polling между командами | Физическое состояние не меняется от wall time или числа GET |
| L27 | Ошибки NaN/Infinity/extra fields/диапазон | Структурированный публичный отказ, без закрытого traceback |
| L28 | Отсутствуют сервер/харнес/LLM друг у друга | Лаборатория запускается самостоятельно; SDK не импортирует харнес |

## 3. Результат разработки

- Репозиторий реализации, воспроизводимый локальный запуск и конфигурация без секретов.
- Migration/инициализация БД, durable worker и restart-инструкция.
- UI, OpenAPI, публичные DTO, транспортный клиент и пример integrate/poll.
- Закрытые сценарии и проверенные эталонные рецепты отдельно от публичного пакета.
- Автоматические тесты L01–L23/L26–L28 по смыслу; UI-проверки основных действий/адаптивности.
- Отчёт приёмки с реальными результатами, известными ограничениями и уточнениями v0.1.

Не считать только красивый макет выполненной лабораторией. Не считать successful smoke научным подтверждением гипотезы.
