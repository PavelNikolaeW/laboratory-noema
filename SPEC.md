# Research Lab v0.1 — продукт и архитектура

## 1. Рабочая ситуация

Человек передаёт агенту работу технолога небольшой лаборатории покрытий:

> Пришла партия материала. Подбери обработку, чтобы получить нужный отклик при допустимых потерях. Оборудование доступно через API. Оставь проверенный рецепт, журнал опытов и условия применимости. Если привычная процедура перестанет работать, выясни причину.

Отклик — условная величина качества материала, не конкретная физическая характеристика. Участнику не требуется химическое образование. Устройство мира должно быть достаточно простым для открытия правил человеком и достаточно составным для переноса знания, планирования и диагностики.

Практический результат — выполненный заказ, воспроизводимый рецепт и подтверждение на свежей порции. Выведение формулы не обязательно для успеха заказа. Точность явных предсказаний оценивается отдельно.

## 2. Состав v0.1

- Источник партий с повторяемыми порциями и конечным запасом материала.
- Весы, термометр, анализатор условного отклика.
- Нагреватель, охладитель, сепаратор, смеситель.
- Разделение порции на две пропорциональные части.
- Асинхронные операции, сохранённые измерения и публичный журнал.
- Заказы с численными критериями, рецептами и независимой проверкой.
- UI человека и HTTP API с одинаковыми экспериментальными возможностями.
- Отдельные служебные средства создания мира, оценки и контролируемых изменений.
- Точные измерения и детерминированные переходы в базовом профиле.
- Один сценарий изменения эффективности нагревателя после базовых сценариев.

За пределами v0.1: настоящая химия, 3D-анимация, генерация сотен устройств, непрерывная физическая динамика, шум и износ по умолчанию, многопользовательское совместное управление одной лабораторией, прямая интеграция конкретной LLM и реализация харнеса.

## 3. Две границы доступа

Публичный контур: заказы, паспорта устройств, допустимые команды, идентификаторы порций, публичное происхождение, измерения, статусы и журнал. Он одинаков по содержанию для человека и агента.

Закрытый контур: истинный состав, скрытая фаза, параметры устройств, формулы, seed, будущие изменения, служебные решения и эталонные рецепты. Только экспериментатор/движок имеет доступ.

Backend лаборатории работает отдельно от REPL. Исходники, конфигурация, БД и служебные логи не монтируются в worker харнеса. Admin API не размещается под теми же участническими credentials: отдельный listener или локальная CLI вне доступной агенту сети. UI участника не получает скрытые поля «для удобства», даже если их не рисует.

Скрытые формулы нельзя доставлять в JavaScript-бандл. Python SDK участника, если создаётся, содержит только транспорт и публичные DTO. Внешние вызовы из харнеса проходят его шлюз возможностей.

## 4. Архитектура для параллельной работы

```text
UI человека → Public HTTP API → сервис операций → движок переходов
                                   ↓                  ↓
                              журнал/состояние ← транзакция

REPL → шлюз харнеса → тот же Public HTTP API

CLI экспериментатора → закрытая конфигурация и оценка
```

Схема выше — описание компонентов, не требование отдельного микросервиса на каждый блок.

Рабочий стек: Python, FastAPI, pydantic v2, SQLAlchemy 2.0; SQLite для однопроцессного локального прототипа либо PostgreSQL при обоснованной необходимости. Выбрать один backend хранения для MVP, не реализовывать два сразу. Фронтенд — простой отдельный клиент или статический UI, обслуживаемый приложением. Конкретный frontend-фреймворк не является частью гипотезы.

Движок — чистые детерминированные функции над состоянием, без HTTP и LLM. Сервис операций отвечает за авторизацию, идемпотентность, блокировки, бюджет и durable commit. Измерения и результаты сохраняются до выдачи события завершения.

## 5. Публичные сущности

| Сущность | Смысл |
| --- | --- |
| Run | Изолированное прохождение человеком или агентом |
| Batch | Партия, из которой можно брать воспроизводимые порции |
| Sample | Физическая порция в пределах условного мира, с историей происхождения |
| Instrument | Устройство с публичным паспортом команд |
| Operation | Принятое выполнение команды |
| Observation | Неизменяемая запись измерения, привязанная к версии образца |
| Order | Заказ с ограничениями и критериями результата |
| Recipe | Машиночитаемая последовательность обработки |
| Submission | Заявка на независимую проверку рецепта |
| Prediction | Зафиксированное до результата предсказание участника |
| Event | Упорядоченная публичная запись о результате операции/оценки |

IDs непрозрачны и не кодируют состав, правильный ответ или параметры. Статусы образца: `available`, `busy`, `consumed`. Любое публичное изменение образца меняет его revision. Старые измерения не изменяются и не выдаются за актуальные.

## 6. Рабочий стол человека

Нужен рабочий инструмент, а не пассивный dashboard.

Главный экран:

1. Заявка технолога: цель, сроки в условных действиях, требования качества/выхода и оставшийся бюджет.
2. Партии и порции: доступные образцы, происхождение и статус; неизвестные свойства обозначены «не измерено».
3. Карточка выбранного образца: последние измерения с указанием revision/времени, история обработки, связанные порции.
4. Доступные действия: оборудование, параметры, объявленная стоимость и подтверждение запуска.
5. Журнал опытов: входы, настройки, выходы, наблюдения и ошибки; фильтрация по образцу/операции.
6. Блокнот: гипотеза, предсказание до действия, вывод после; текст сохраняется сервером внутри run.
7. Рецепт: редактор последовательности шагов и отправка на проверку.

Минимальные визуальные представления: сравнение выбранных порций, история происхождения, график выбранного измерения по выбранной настройке из уже полученных данных. Не рисовать идеальную скрытую кривую и не интерполировать её как установленный закон. При малом числе наблюдений достаточно таблицы/точек.

Любая сводка UI строится из публичных данных и доступна агенту через те же исходные записи. UI не подсказывает «правильный следующий опыт». Человек может локально сравнивать/считать, как агент в REPL.

Сохранение заметок и прохождения переживает обновление браузера. Кнопка повтора HTTP-запроса использует тот же idempotency key; новая экспериментальная попытка — новый ключ. В интерфейсе видны accepted/running/succeeded/failed, а сетевой таймаут не называется неудачей обработки.

## 7. Реализм работы и ограничения

Порции расходуют запас партии. Разделение и смешивание не создают материал. После потребляющей операции нельзя повторно использовать старую порцию. Нагрев/охлаждение меняют существующую порцию, сепарация и смешивание создают новые с цепочкой происхождения.

Время в базовом мире дискретно: нет скрытого остывания от длительности размышления или HTTP polling. Задержка операции — транспортная/организационная; химическое состояние меняется только командами. Человек и агент не получают разные результаты из-за разной скорости чтения.

Паспорт объясняет, как управлять устройством, какие единицы/диапазоны допускаются и сколько стоит команда. Он не раскрывает зависимость результата от скрытого состава. Ошибки не содержат приватных значений.

## 8. Воспроизводимость и критерий готовности

Каждый run создаётся из versioned конфигурации. Реализация и приватный hash конфигурации фиксируются до сравнения. Одинаковые начальные состояния и команды дают одинаковые состояния в базовом профиле, кроме непрозрачных ID и часов транспорта.

Человек и агент работают в независимых копиях мира, а не загрязняют опыт друг друга. Знания разработчика и ознакомление с формулами помечаются при оценке человека; это не слепой baseline.

Готовность MVP: человек из браузера получает заказ, экспериментирует, сохраняет и проверяет рецепт; внешний клиент делает то же через API; операция переживает рестарт и безопасный повтор; скрытые правила не попадают в публичный контур. Полный список проверок — в IMPLEMENTATION_AND_ACCEPTANCE.md.
